# 2026-10-05：流水与发票台账的修改联动

继续 T4 的版本与恢复工作，承接 `c496578`、`ff57431` 的明细修改能力。用户已授权持续按计划推进；保持第三方流水只读、Seal 规则外部维护、识别与审核提供方独立。

## 问题与实现

直接流水/台账编辑没有触发；新增同票号台账行会影响已有明细的查重证据，不能只通知新发票自己的明细。仅使用已经保存的审核依赖也可能漏掉首次审核正在读取但尚未落盘的任务。

- 新增独立 `review.resubmit_on_source_change`，与明细开关分别配置，默认关闭，仅搭配 `after_recognition`。企业配置显式保持两个修改开关关闭，原识别完成自动送审不变。
- 飞书输入适配器只把配置来源中实际参与审核的字段变化转为中立通知。流水只保留来源/记录标识；台账保留修改前后票号线索，绝不拿事件值替代当前事实。未知线索保守扩大重新读取范围。
- 收件记录先持久化，后台读取同一业务范围的已存快照，按真实支付来源、关联 ID、本票台账 ID、历史候选 ID、新增/变更票号定位明细。已有审核快照之外，保守覆盖等待/执行中的自动任务，避免首次审核尚未保存依赖时丢修改。
- 全部目标意图保存后才确认收件记录。部分失败后恢复；事件标识与首次接收时间稳定，不延长已排队明细的原等待期限。原有审核版本去重继续阻止重复付费。
- 换来源时旧通知保留，不重定向。收件范围字段使用 `review_scope`，区别于自动意图的 `source_scope`，避免同目录的持久化记录被当成另一类任务。发票来源更换时仍由当前实际准备入口核对完整台账和事实。
- 人工审批、锁定、申领状态、派生概要和反向关联不触发来源重审；原生关系变化由明细开关处理。识别采用纯轮询时，启用任一修改开关也需要长连接。

## 本地验证

事件测试验证字段过滤、同一记录多动作合并、修改前后 JSON 文本及富文本票号、缺失/未知线索、新增/删除、存储失败不确认，以及真实数值不进入支付通知。装配和配置测试覆盖提供方独立的监听条件、关闭支付时不监听、纯轮询识别仍需事件、开关与必要票号字段约束。

`go test ./...`、`go vet ./...`、`go test -tags no_anthropic ./...`、默认与外部主线构建通过；审核、事件、配置及装配的 `-race` 检查通过。真实只读依赖/准备及运行更新另行记录。

## 边界

本阶段不宣称已经开启企业开关或完成真实编辑后的付费审核回调。开关关闭时不接收修改任务；停机丢失的事件仍未补扫。历史依赖和未知票号可能增加读取，但实际事实未变时不新增审核版本。

Seal 接口明确同一 `sourceInvoiceId` 的核心事实修改会返回冲突，见[接口原文](../../external-api/sealai/webhook-document.md)。来源联动不改变该 ID 绕过验真、占用或查重，明确拒绝仍保存为 `failed`；后续需可见的对账与处理入口。读取、事件排队、人工显式提交和回写不是跨系统事务；业务冻结、历史占用、分摊、撤回及飞书人工审批继续独立推进。
