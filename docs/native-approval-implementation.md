# 原生人工审批接入：下一阶段实现约定

2026-10-05，承接 `929cbf1` 的实例客户端与实时模板映射。本文件细化 T6 后续实现，保持用户授权的完整业务目标；不是已经实现的功能清单。实际接口与身份核对见[过程记录](progress/2026-10-05-native-approval-client.md)。

## 配置与业务输入

人工审批另设显式配置，仍由选中的业务来源文件确定流水、明细与台账。目标应用必须明确选择当前桥接应用或旧审批应用，不能因 Code 不可读而回退；open ID、部门、审批人和审批附件都属于目标应用/企业的身份范围。跨应用或跨租户映射必须显式提供并验证，不能匹配同名员工。

分组轴由配置列出，日期取自配置字段并明确时间区间及时区；项目与特性取稳定字段/关联 ID，不按显示名称分组。允许显式选定记录组，定时选择是后续独立入口；不能把某个历史阈值或固定月份写入核心。模板映射使用现有 `DetailFormBinding`，运行时校验完整必填结构及流程中需要发起人指定的审批人。

首次准备应读取实际明细、关联流水、完整发票及已存审核结果。逐条保存来源 scope、record ID、审核 document ID/revision、当前事实版本与最终业务值。当前 AI 结果必须与准备时事实匹配；`delivered=true`、AI 列有值或同名 DocumentSN 均不能代替版本匹配。是否允许某类 AI 建议进入人工审批属于显式业务策略，不推断 Seal 内部规则。

## 共用编排与供应商边界

- `core/approval` 定义业务行、来源版本引用、分组、冻结计划及稳定身份，不导入飞书 SDK，不描述 `fieldList`、`widget...` 或 native form JSON。金额继续复用精确十进制规范。
- `app/approval` 负责读取/准备、提交前事实重核、持久化领取、建单和 UUID 对账；只依赖小接口。来源适配器负责字段、关联和人员转换，Feishu gateway 负责当前模板映射、上传与实例协议。
- 同一准备计划的 UUID 由明确来源、目标身份/模板、配置版本、分组、发起人及排序后的明细版本决定；不能靠随机新 UUID 消除未知状态。
- 在任何建单调用前，原子保存完整计划及成员预约。同一明细不能同时进入两个活动审批组，即使组大小、日期或模板改变；版本去重不足以保证这一点。单主机文件实现可先按来源范围串行化，后续数据库应实现相同约束。

## 建单状态与恢复

| 情形 | 本地处理 |
| --- | --- |
| 准备失败、旧 AI 版本、缺字段或身份不明 | 只返回具体阻塞条件，不创建实例 |
| 同一计划已建单 | 返回原实例映射，不再次发送 |
| 调用前领取成功 | `submitting`，完整 UUID/来源版本已持久化 |
| 响应失去或创建协议不完整 | `unknown`，保留预约；按原 UUID 查询 |
| UUID 冲突 `60012` | 按原 UUID 查询，不能作为未建单的证据 |
| 查询得到实例 | 校验 UUID、模板、目标应用与发起人；保存真实实例 Code 和状态 |
| 查询失败、权限不足或暂未找到 | 保留未知，不因一次未找到自动换 UUID 或重发 |
| 明确的创建拒绝 | 保存安全分类；只有已证明未创建才能解除建单预约 |
| 多个实例/回调竞争 | 原子更新、不覆盖已确认映射，冲突进入对账 |

结果读取不依赖当前新配置的模型或 Seal 密钥；旧模板版本的 pending 实例继续按其原 UUID/目标身份对账。模板、来源或租户更换不得重定向旧任务。上传结果也要独立保存，不能因建单/回写失败反复生成附件；Base token 不能作为审批 file code。

## 人工结果与财务边界

人工状态先持久化，再按已冻结的成员版本回写专用人工列。来源改变时保留原决定及映射，给出需要处理的版本冲突，不能静默将批准套到新事实。状态事件是读取真实实例的触发信号，不能单凭事件里的状态覆盖历史结果；重复、乱序、撤销和服务重启都要可恢复。

Feishu 人工结果、Base 回写及 Seal `manual-result` 是独立交付任务，任一失败不应丢失人工决定或再次建单。平台退回重提、修改原表单和按原表单再次提交当前被关闭；支持前需补齐来源版本映射与新旧实例关系。

审批通过不代表付款或结算完成。预约释放、历史占用、合法分摊、金额冻结、撤销与已结算冲正分别需要明确事实和策略，不能用票号候选或 `CANCELED/DELETED` 单一状态推断。未确认的释放策略保持显式待处理，不通过删除状态文件解锁。

## 受控验收顺序

1. 共用分组与状态库：排序稳定、多行引用、当前审核版本门禁、并发成员预约、部分持久化失败、旧来源隔离。
2. Feishu gateway：当前模板映射、同应用人员、审批附件、创建超时后的同 UUID 查询及错误分类。
3. 配置与只读预览：真实企业下输出完整阻塞原因/计划，零创建、零上传、零通知。
4. 真实建单：完成目标企业、发起人、审批人及完整表单配置，形成具体可审阅请求后执行受控新测试实例；不操作历史审批。
5. 人工结果闭环：重复/乱序事件、版本改变、Base 或 Seal 部分交付失败、撤回/退回重提及重启恢复。

每一阶段独立提交代码与证据。真实资源配置未齐时继续完成可验证的编排，不把 fake 或本地表单通过写成真实人工审批验收，也不据此宣称完整业务已完成。
