## 规则与真实审核行为

[审核规则页](https://mediastorm-test.sealai.cc/audit/training/rules)显示规则集版本 2，所有改动均已发布，两条生效规则均为「必须遵守」：

2. 校验发票与报销消费场景的合理性。

**这些规则在 Seal 内维护，本项目不加载、不复制执行 Seal 规则。** 页面说明审核使用最新发布版本；现有 Webhook 契约不提供指定规则版本。桥接服务的业务修订号只能标识本地输入与通道配置，不能代表已锁定 Seal 规则版本，也不能据此实现“规则更新后强制重审”。

## 本轮已修正的输入缺口

原 Seal 查重字段只有来源、候选记录 ID 与标记，缺少核对候选本身的事实。现在从台账有效列读取商户、票号、票据类型、日期、金额、币种，以 JSON 文本随候选发送；日期统一成 ISO 日期，金额保持十进制文本。两种审核提供方共用这些候选事实，版本计算也纳入它们。

每份 Seal 请求都会发送 `duplicate_evidence_scope`，说明按票号查候选的覆盖边界：缺票号未查询；无候选不证明无重复；候选不证明已经审批或结算；不同票号、其他来源及完整历史费用尚未覆盖。该字段描述证据范围，不作审批决定。

飞书只读核验确认配置中 `source_key`、`invoice_number`、`seller`、`receipt_type`、`issue_date`、`total_amount`、`currency`、`raw_json` 均能定位线上字段；日期为日期类型，金额为数字类型，其余为文本。已成功读取少量记录，未写入业务数据。

## 下一步验收顺序

1. 部署持久状态与 HTTPS 接收端，核对入口日志的密钥遮蔽；本地健康检查成功不等于 Seal 可访问。

3. 配置通道回调 URL，用 `submit-review` 生成状态库中已知的新任务，验收真实回调、重复投递、写入失败恢复和旧版本隔离。
4. 对含历史候选的样本验收 Seal 实际读取候选事实；新增的输入字段目前通过本地测试，尚未重新付费送审。
5. 扩充历史关联、分摊与审批/结算事实来源，再验收重复报销场景。Seal 规则调整仍在 Seal 系统进行；自有 Anthropic 审核才配置本地规则。
