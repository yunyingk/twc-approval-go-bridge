# 架构迁移任务与验收

配套 [架构评审](architecture-review.md)，基线 `7624896`，2026-10-03。任务尚未实施；这是供后续结对工作的建议顺序，不是直接授权大规模重构或线上写操作。

上述为评审时的计划快照。后续用户已授权实施；当前落地内容和剩余边界见 [运行与交接说明](runtime-and-handoff.md)。Seal 的规则由 SealAI 维护，T3/T4 中的本地规则前置仅适用于自有审核。

## 开始前

1. 读 AGENTS、当前 README 和评审；核对代码是否已变化。本文件列的是目标，不能作为现状报告。
2. 每次只领取一个有闭环验收的任务，先对齐涉及的重大结构或业务变化；保留原注释、既有行为和历史数据。
3. 本地契约测试优先使用脱敏固定样本和 fake，不调用付费模型或写线上数据。真实接口验证使用项目应用身份，不能改用用户 OAuth。
4. 实际改代码后执行相关测试、`go test ./...`、`go vet ./...`；涉及模型装配时补充 `go test -tags no_anthropic ./...` 与对应构建检查。

## T1：抽出共用识别用例，行为保持不变

**范围**：`anyreceipt/flow`、`anyreceipt/ledger`、`feishu/base/events`、`cmd/server`。

- 附件任务调度和结果交付迁至 `app/recognition`。
- 将飞书事件 JSON 解码留在飞书输入适配器，转换成用例输入；轮询与事件继续共用处理路径。
- 将飞书台账字段映射放回飞书适配层，用例只依赖必要的结果写入接口。
- 这一步暂时保留旧识别数据结构，不同时改字段与主键。

**验收**：默认 Anyreceipt 和模型装配均走相同用例；事件过滤、轮询首次基线、附件去重及台账回写既有测试保持通过；`app` 不导入供应商包或飞书协议类型。

**边界**：此次拆分不等于已经解决持久化、重启恢复或字段中立化；交接时明确剩余问题。

## T2：建立标准识别事实及历史兼容读取

**范围**：`core/invoice`、Anyreceipt 和模型适配器、台账读写、Seal mapper。

- 明确币种、精确金额、缺失值、识别元数据和数据质量问题；决定多票附件的首版支持范围。
- 供应商键只在其归一化/历史解码边界出现，公共台账逻辑与 Seal mapper 读取标准字段。
- 原始 JSON 与标准快照分离；给存储表示加版本，兼容已有 `outputs` / `data.outputs` 数据。
- 明确人工修正的有效值优先级与审计来源。保留现有来源键和外部追踪号，另行设计新身份迁移。

**验收**：两家识别实现的等价样本产生一致业务事实；缺币种不猜、缺金额不等于零；原始响应可追溯；人工修正后查重与送审使用相同有效事实；旧台账仍能读取。对暂不支持的多票输入有显式处理结果。

**禁止捷径**：只把 `Outputs` 改名为 `Fields`，或只让模型继续仿写 Anyreceipt JSON，就宣称已中立化。

## T3：建立可替换审核契约，先接现有 Seal

**前置**：与用户对齐审核输入范围、缺失数据处理和结果含义；标准票据事实稳定。

- 新增 `core/review` 输入输出与 `app/review` 用例，接口表达请求审核及应用结果。
- 从 `seal/review` 抽出读取、就绪核验、聚合与查重编排；上传原件、`seal/mapper`、Seal 响应转换留在 Seal 实现。
- 飞书数据读取不再返回 `seal/review` 类型；公共结果不再暴露 `seal.SubmitResponse`。
- 加入独立审核提供方配置；保持现有显式命令兼容，并明确 `submit-seal` 是固定 Seal 入口还是迁移为新中立命令。不能让旧命令悄悄改变含义。
- 用 fake 审核器验证替换边界即可，不要求此时实现真实自有审核。

**验收**：替换 fake 时不需要 Seal DTO、上传 ID 或 Seal URL；同步结果与异步完成均进入同一结果处理用例；缺少规则明细不伪造；只有识别开启时不要求审核密钥，审核未启用时不自动送审。

## T4：冻结快照，补齐持久化与主线审核闭环

**前置决策**：存储与部署方式、显式提交/冻结信号、版本变化规则、真实回调鉴权及结果字段；缺少决定时先提交具体方案，不能自行套历史阈值。

- 保存报销快照、审核尝试、提供方版本和本地/外部 ID 映射。
- 保存识别任务及交付状态，避免只因飞书回写失败就重复付费识别；定义永久失败与可重试错误。
- 可靠接收真实 Seal 回调，统一处理重复、乱序、未知关联和飞书写失败；保留 mock 的本地测试定位。
- 外部请求结果不明时进入可恢复状态。仅使用已经确认的幂等或查询协议，不臆造供应商状态查询接口。
- 业务状态日志至少能串起来源、版本、任务、审核尝试、外部引用和回写结果；健康端点成功不能当作链路验收。

**必测场景**：

| 场景 | 应有结果 |
| --- | --- |
| 重启发生在 OCR 成功、台账写入前 | 恢复交付，不丢任务；已有结果可复用 |
| 发送审核后超时，外部可能已经受理 | 保留结果未知与原尝试映射，不能盲目创建另一张单 |
| 审核途中新增/删除附件或修改金额 | 新版本与旧尝试可区分，旧结论不覆盖新版本 |
| 回调重复、迟到，或先于提交响应到达 | 可关联、暂存或隔离并恢复，结果只应用一次 |
| 回调已保存但飞书暂时不可写 | 可独立重试回写，不重新调用审核器 |
| 两个执行者同时领取同一任务 | 原子领取或明确的单实例限制，不把内存 map 视为多实例保护 |

**验收**：Anyreceipt + Seal 的受控送审、真实结果接收与飞书回写闭环完成后，再声称主线审核可用；自动送审另需提交信号与并发修改验证。

## T5：按能力逐项验收自有替代

识别部分可以在 T2 后推进；审核正式替换依赖 T3、T4 及已确认的规则集和事实来源。

- 识别：完善结构化输出、截断/非法响应处理，确认 PDF/多页策略；不以“修掉 Markdown 围栏”作为全部验收。
- 审核：共享同一报销快照及规则集，确定性校验由代码执行，语义分析调用独立 Anthropic 客户端。
- 使用固定脱敏样本评估字段提取、资料不足、查重证据、规则判断和人工复核路由；错误、耗时、费用也记录。
- 覆盖四种提供方组合；当前不支持的组合要明确报错，不能成功启动后悄悄绕过能力。
- 对照评估结果单独保存，不能让影子评估修改正式台账或产生第二份正式审批。

**验收**：业务口径一致，差异能解释，失败可恢复；禁用 Anthropic 的构建仍可运行外部主线，选择自有能力则明确报错。实测覆盖不足时注明“部分替代”。

## T6：飞书人工审批与后续扩展

与自有能力开发分开推进，避免把完整业务闭环推迟到模型能力全部完成以后。

- 确认日期/项目/特性等分组规则，以及 AI 结论如何影响人工流程；模板创建成功不等于实例流程已实现。
- 保存审批组到明细版本的映射，核对跨租户人员身份、附件上传及模板控件 ID。
- 人工结果、撤销与退回回写走业务用例；若需同步 Seal `manual-result`，作为独立外部交付处理，失败不丢失人工决定。
- 历史占用、合法分摊、结算及权限锁定分别核对业务事实与平台能力，不由票号相似直接推断。

**验收**：一组多明细与实例双向可追溯；重复触发不重复建单；撤回、退回重提和部分回写失败有明确处理。每项真实写操作按当次授权与仓库规则执行。

## 后续模型的交接格式

每次交接只需说明：完成的任务编号、修改的边界、保留的兼容性、运行过的验证、尚未覆盖的真实场景，以及下一项具体前置条件。若改变上述方案，同步解释原因并更新本文；不要把预期功能写进“已完成”。
